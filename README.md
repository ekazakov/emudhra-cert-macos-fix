# eMudhra macOS — JavaScript + zx

Полная JS-версия комплекта для проверки CA, обратимого изменения `/etc/ssl/cert.pem` и ежедневных уведомлений macOS. Комментарии к операциям и проверкам написаны на русском языке.

## Требования

- macOS; Node.js **22.15+**; npm.
- Пакет [`zx`](https://google.github.io/zx/) устанавливается локально через `npm ci` из lockfile.
- `sudo` требуется **только** при реальном удалении или восстановлении системного CA-bundle.
- Стандартные `/usr/bin/security`, `/usr/bin/curl`, `/usr/bin/osascript`, `/usr/bin/plutil`, `/bin/launchctl` необходимы для соответствующих функций ОС. Замена bundle выполняется средствами Node.js.
- Python 3 используется *только* для чтения его собственного SSL-контекста и для необязательных сетевых TLS-тестов Python. Для остального используются JS, Node `crypto.X509Certificate`, `fs` и `tls`.

## Установка

Из каталога проекта:

```bash
npm ci
node check-emudhra-certs.mjs
node check-emudhra-certs.mjs --live
node check-emudhra-certs.mjs --live-all
node check-emudhra-certs.mjs --json
```

Вместо `sh script.js` используйте **`node script.mjs`**. Все скрипты написаны как ES modules. Пакет `zx` нужен для системных вызовов, но большая часть логики работает на чистом JS.

## Удаление корней с резервной копией

```bash
node remove-emudhra-certs.mjs --dry-run --include-aaa
sudo "$(command -v node)" remove-emudhra-certs.mjs --include-aaa
node check-emudhra-certs.mjs --live
```

Без `--include-aaa` удаляется **только** `emSign ECC Root CA - G3` (если он присутствует). С флагом также удаляется `AAA Certificate Services`, что **может нарушить легитимные TLS-подключения**. Скрипт сверяет точные SHA-256 этих корней, их заголовки из формата Apple и число сертификатов до и после; создаёт неперезаписываемую резервную копию в `/etc/ssl/cert.pem.emudhra-backup.YYYYMMDD-HHMMSS.PID`.

### Восстановление

```bash
node restore-emudhra-certs.mjs --list
node restore-emudhra-certs.mjs --backup /etc/ssl/cert.pem.emudhra-backup.YYYYMMDD-HHMMSS.PID --dry-run
sudo "$(command -v node)" restore-emudhra-certs.mjs --backup /etc/ssl/cert.pem.emudhra-backup.YYYYMMDD-HHMMSS.PID
```

Замените путь на конкретное имя из `--list`. Дополнительно принимается `/etc/ssl/cert.pem.orig`. Скрипт создаёт копию **текущего** bundle `cert.pem.before-restore.*` до замены.

Если содержимое отличается не только двумя целевыми корнями, восстановление **запрещено**, поскольку иначе можно отменить обновление безопасности Apple. Опция `--force` снимает этот запрет, но применять её следует только после осознанного сравнения версий. После восстановления повторите `check --live`: возвращение корней может снова разрешить опасные цепочки.

Удаление и восстановление проверяют резервную копию, записывают и синхронизируют кандидата в приватном каталоге рядом с bundle, затем заменяют файл через `rename`, сохраняя владельца и POSIX-права. Символьные ссылки на файл и файлы с дополнительными жёсткими ссылками не принимаются для изменения. Наши CLI используют блокировку `cert.pem.emudhra-lock`; после аварийного завершения она может остаться. Удалять её вручную можно лишь убедившись, что операция больше не выполняется.

Непосредственно перед заменой повторно проверяются inode и SHA-256. Это обнаруживает изменения во время подготовки, но не обеспечивает общей блокировки с обновлениями macOS: не выполняйте обе операции одновременно. ACL, extended attributes и file flags при замене не переносятся. Если проверка после записи не проходит, скрипт сообщает ошибку и путь к бэкапу; автоматического отката поверх возможных чужих изменений нет. `--force` никогда не разрешает повреждённый или пустой PEM.

## Настройка pip и pip3 текущего пользователя

`fix-pip-certs.mjs` задаёт `[global] cert = /etc/ssl/cert.pem` в пользовательском `pip.conf`. Запускайте **без sudo**:

```bash
node fix-pip-certs.mjs --dry-run
node fix-pip-certs.mjs
```

Путь определяется по правилам установленного Apple pip: обычно `~/.config/pip/pip.conf`, а если соответствующий каталог уже существует — `~/Library/Application Support/pip/pip.conf`. Учтены различия версий pip и XDG через внутренний API установленного pip; если API недоступен или имеет неизвестный формат, команда отказывает до записи. Для определения пути и проверки результата используется `/usr/bin/python3`; файлы внутри Xcode и `sitecustomize.py` не изменяются.

Команда:

- проверяет корректность системного CA-bundle и сообщает REVIEW, если в нём остались целевые CA;
- сохраняет комментарии, переносы строк, многострочные значения и остальные настройки pip.conf;
- отказывает при другом `cert` в проверяемых пользовательских, системных и относящихся к этому Python конфигурациях; существующий корпоративный CA-bundle не заменяется молча;
- в dry-run показывает все конфликты `PIP_CONFIG_FILE`, `PIP_CERT`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE` за один запуск и позволяет просмотреть план; реальное применение при этих конфликтах запрещено. Переменные не изменяются. `trusted-host` отмечается предупреждением и не удаляется;
- создаёт эксклюзивный проверенный бэкап существующего файла `pip.conf.emudhra-backup.*` с правами 0600, затем атомарно заменяет файл; новый pip.conf создаётся с правами 0600, у существующего сохраняются POSIX-права;
- проверяет записанный файл и подтверждает значение настоящей командой `pip config --user get global.cert`;
- при повторном запуске не переписывает уже настроенный файл и не создаёт лишний бэкап. Dry-run не создаёт файлов или каталогов. Запуск через sudo отклоняется.

Бэкап может содержать токены/пароли из исходной конфигурации: не публикуйте его. Кандидат целиком в консоль не выводится. Некорректный INI, неподходящая кодировка, символьные/дополнительные жёсткие ссылки и небезопасные права приводят к отказу с кодом 2. Ошибка до атомарной замены оставляет исходный файл неизменным; ошибка проверки после записи требует изучить текущий файл и бэкап, автоматического отката поверх чужих изменений нет. Блокировка `pip.conf.emudhra-lock` защищает только от наших параллельных CLI. После аварии она может остаться; удаляйте её лишь убедившись, что процесс завершён. ACL/xattrs не переносятся, совместной блокировки со сторонними редакторами нет.

Настройка относится к **pip текущего пользователя**, включая совместимые pip3, Homebrew pip и pip в venv, если они читают этот файл. Отдельные окружения могут выбирать иной пользовательский путь. Приоритеты и пути описаны в [документации pip](https://pip.pypa.io/en/stable/topics/configuration/): конфигурации venv, переменные окружения и аргументы команд могут переопределять значение, а `pip --isolated` игнорирует пользовательский файл. Проверка относится к Apple pip в текущем окружении; она не доказывает применение во всех установках и не выполняет сетевой тест. Для других Python проверьте `python -m pip config debug` и фактическое TLS-поведение отдельно.

Скрипт только выбирает CA-bundle: он не удаляет сертификаты. Сначала подготовьте `/etc/ssl/cert.pem` средствами проекта, а после обновлений macOS повторите аудит этого файла. Ранее предложенный способ через sitecustomize удалён из команды, поскольку запись внутрь Xcode.app может завершаться EPERM даже с sudo. Если старый управляемый блок был добавлен вручную, новая команда его не удаляет; проверьте его отдельно, поскольку он задаёт PIP_CERT с более высоким приоритетом.

Для отмены, если `cert` ранее отсутствовал, выполните:

```bash
/usr/bin/python3 -m pip config --user unset global.cert
```

Если требуется восстановить бэкап целиком, сначала сравните его с текущим файлом, чтобы сохранить более поздние настройки. Бэкап восстанавливается только по вашему явному выбору; команда не выбирает его автоматически.

## Ежедневный запуск через launchd

```bash
node install-emudhra-monitor.mjs --time 09:00
# Дополнительно проверять TLS напрямую через текущие Node/Python:
node install-emudhra-monitor.mjs --time 09:00 --live-all
```

Установщик запускается **без sudo**. Он помещает JS-файлы и `node_modules` в `~/Library/Application Support/eMudhraAudit` и регистрирует пользовательский LaunchAgent `local.emudhra.certificate-audit`. Передача в `launchd` **абсолютного пути к Node** сохраняет работоспособность при минимальном PATH, но после удаления/обновления менеджером версий этого Node нужно переустановить монитор.

```bash
# Тест локального Notification Center:
"$(command -v node)" "$HOME/Library/Application Support/eMudhraAudit/run-emudhra-monitor.mjs" --test-notification
# Немедленный запуск в launchd:
launchctl kickstart -k "gui/$(id -u)/local.emudhra.certificate-audit"
# Полный журнал проверок:
tail -n 100 "$HOME/Library/Logs/emudhra-certificate-audit.log"
# Удаление расписания, без удаления журналов:
node install-emudhra-monitor.mjs --uninstall
```

Монитор проверяет системный `curl` в режиме `--live`, а в режиме `--live-all` ещё Node.js и обнаруженные Python. Уведомления отправляются только при **новых или изменившихся** находках либо изменении набора недоступных источников. Состояние доставки сохраняется после успешного вызова `osascript`; при его ошибке следующий запуск повторит попытку. Успешный вызов не гарантирует видимость баннера при отключённых уведомлениях или Focus.

При обновлении установщик останавливает предыдущую службу перед копированием файлов. Ошибки `launchctl print`/`bootout` не скрываются, кроме явного отсутствия службы. Если копирование, проверка plist или `bootstrap` завершились ошибкой, расписание может оставаться остановленным: устраните причину и повторите установку. Установка не является транзакцией.

## Что означает отчёт

В интерактивном терминале выделяются только ключевые слова: `REJECTED` — зелёным, `UNKNOWN` — жёлтым, `ACCEPTED` — красным. В скрипте удаления `DRY-RUN` жёлтый, `ERROR` красный, «Готово» зелёное. Переменная `NO_COLOR` (включая пустое значение) отключает цвет; терминал `TERM=dumb` также получает обычный текст. При перенаправлении соответствующего потока в файл или pipe цвет отключён. JSON `--json` и журналы монитора не содержат добавленных цветовых кодов.

Ненулевые счётчики `emSign=…`, `AAA=…`, статус `REVIEW` и описание найденного корня выделяются жёлтым; нулевые счётчики остаются обычными. Статус `COMPROMISED` и описание точно идентифицированного скомпрометированного intermediate выделяются красным. В удалении названия запланированных к удалению корней жёлтые. Итоговая строка `RESULT` целиком зелёная при `exit=0`, красная при `exit=1`, жёлтая при `exit=2`.

- **REVIEW** — корень найден в проверяемом хранилище; само по себе это **не доказывает уязвимость**.
- **COMPROMISED** — найден точный SHA-256 одного из 16 известных скомпрометированных промежуточных CA, включая code-signing.
- **ACCEPTED** — TLS-клиент принял тестовую цепочку; это более сильный сигнал, требующий устранения.
- **REJECTED** — TLS-клиент отказал по причине проверки сертификата.
- **UNKNOWN** — таймаут, сетевой сбой или недоступность хранилища; **не означает безопасность**.
- Exit codes: `0` — нет находок/неопределённостей в проверенной области; `1` — есть находки (возможен также `unknown`, проверяйте JSON); `2` — неполная проверка без находок либо ошибка CLI.

Keychain отображается информационно. Присутствие корневого CA в Keychain не означает, что встроенные API Apple доверяют скомпрометированным промежуточным сертификатам. Встроенные версии `pip` могут иметь отдельный certifi. Скрипт не охватывает автоматически все контейнеры, venv, Electron-приложения или версии Node/Python, установленные через `mise`/`pyenv`. Для сетевых тестов через прокси результат может отражать доверие прокси, а не самого клиента.

## Расширенные проверки клиентов

`node check-emudhra-certs.mjs --live-all` проверяет четыре публичных тестовых HTTPS-хоста через обнаруженные клиенты. Без сетевых флагов выполняется только обнаружение/чтение конфигурации. `--live` по-прежнему проверяет сеть только системным curl. У расширенного прохода может быть заметно больше времени выполнения: таймаут ограничивает каждую пробу, но клиенты проверяются последовательно.

- `[INFO] … certifi (package inventory)` — содержимое поставляемого пакета, не доказательство активного доверия. Корни в таком инвентаре сами по себе больше не вызывают REVIEW/exit=1. Точные скомпрометированные intermediates по-прежнему отмечаются независимо от роли файла.
- `[CLIENT] … pip` и `requests` — версия, выбранный CA-bundle и тип SSL-контекста. PipSession строится из опций установленного pip с чтением его конфигурации; запрос учитывает CA-переменные окружения. Современный pip может добавлять системное доверие через truststore: один путь bundle не описывает весь контекст.
- `[REJECTED/ACCEPTED/UNKNOWN] … pip` — отдельная HTTPS-проба настоящим PipSession, а не Python ssl. Выполняется GET с закрытием ответа, без установки пакетов, редиректов и загрузки тела. Keyring/netrc-аутентификация отключена для тестовых хостов. Неизвестная версия внутреннего API pip даёт UNKNOWN.
- Git, OpenSSL/LibreSSL, Homebrew curl, wget, Ruby Net::HTTP, RubyGems, Bundler, Perl LWP/HTTP::Tiny, npm, pnpm и Yarn Classic проверяются при обнаружении. Версии системных/Homebrew/PATH executable дедуплицируются по realpath. Отсутствующие компоненты отмечаются NOT_INSTALLED, ошибки установленного клиента — UNKNOWN. У npx показывается связь с npm; произвольные пакеты через npx никогда не запускаются.
- Для Git читаются URL-настройки CA и sslVerify; у npm/pnpm/Yarn — cafile и strict-ssl. Полная конфигурация, registry tokens и proxy passwords не выводятся. Тесты CLI запускаются из временного каталога: настройки конкретного проекта не охватываются.
- **Git и npm/pnpm/Yarn выполняют сеть с изолированным HOME/config**, куда переносятся только настройки CA/проверки TLS (у Git также sslBackend/CAPath) и переменные путей CA. Пользовательские токены, Git auth headers/cookies, NODE_OPTIONS, proxy settings и auth-конфигурация не наследуются. Клиентские сертификаты RubyGems/Bundler тестовым хостам не отправляются: при их наличии проба даёт UNKNOWN. Поэтому их сетевой результат относится к этому явно указанному scope, а не ко всей пользовательской конфигурации. Corepack shims не запускаются, чтобы не скачивать менеджеры. Для modern Yarn неподдерживаемый сетевой адаптер даёт UNKNOWN.
- Java: наличие macOS `/usr/bin/java` не означает установленную JVM. Ищутся JDK через java_home, JAVA_HOME, типовые каталоги и PATH; если JVM нет, выводится NOT_INSTALLED. Для установленного JDK компилируется временная проба стандартного JSSE HttpsURLConnection, выводится версия/настройка trustStore. Нужен javac; JRE без компилятора даёт UNKNOWN. Java-библиотеки и Maven/Gradle-проекты отдельно не охватываются.

HTTP 404/401 после установленного TLS может означать ACCEPTED: содержимое тестового сайта не обязано быть git-репозиторием или npm registry. DNS, timeout, неизвестные CLI-флаги, ошибки прокси и неподдерживаемые API не считаются отклонением сертификата. Известные отключения TLS-проверки вызывают REVIEW. Совпадение по версии/имени файла не используется как доказательство безопасности.

Расширение от 02.11.2026: 53 автоматических теста прошли. Проверено локальным TLS-сервером с искусственным CA и реальным PipSession. Read-only интеграция на публичных хостах подтвердила REJECTED для установленного pip, Python ssl, curl, Node, Git, OpenSSL/LibreSSL, wget, Ruby, RubyGems, Bundler и HTTP::Tiny. У LWP и отдельных версий пакетных менеджеров остаются UNKNOWN — это не безопасность. Java на этой машине не обнаружена, её сетевой адаптер здесь не проверен. После обновления кода переустановите существующий монитор, чтобы он получил новый src/clients.mjs; расписание автоматически не меняется.

## Тесты

Исправления после ревью: ошибка чтения TLS-настроек запрещает изолированную сетевую пробу и даёт UNKNOWN; только отсутствующий ключ Git (exit 1 без диагностики) считается default. Offline-ошибки Ruby/Perl и неуспешные процессы также отражаются как UNKNOWN. Git sslVerify нормализуется через `git config --bool`. У pip учитываются trusted-host и insecure-адаптеры, даже если session.verify содержит обычный путь CA. Bundler использует тот же fallback CA и клиентского сертификата из RubyGems, что и его реальное соединение; клиентский сертификат из любого источника останавливает пробу до создания соединения. Новые регрессии проверяют отсутствие ложного exit=0, приоритет настроек и сохранение обычного поведения без клиентской идентичности.

```bash
npm test
```

Тесты используют искусственные X.509-сертификаты, создаваемые **только для тестов** через OpenSSL, и публичные сертификаты из первоисточника в `tests/fixtures` (снимок от 01.11.2026). Закрытых ключей инцидента в проекте нет. Файловые изменения выполняются во временных каталогах; TLS-тест таймаута открывает локальный TCP-порт. В ограниченной песочнице для него может потребоваться разрешение. `zx` устанавливается настоящим `npm ci`, без тестовой замены.

**Проверка 01.11.2026:** 30 тестов прошли на macOS arm64 с Node.js 26.13.0, npm 12.2.1 и zx 8.8.5. Проверены реальные read-only вызовы Keychain, curl, Python, Node TLS, `plutil`, оба dry-run удаления. Системный curl и `/usr/bin/python3` приняли все четыре тестовые цепочки; текущий Node.js и найденные Homebrew Python отклонили их. Реальная установка/переустановка LaunchAgent, `bootstrap`/`bootout`/`kickstart`, отображение уведомлений, работа после сна/перезагрузки и запись системного bundle не проверялись. Подробности: [AUDIT.md](AUDIT.md).
